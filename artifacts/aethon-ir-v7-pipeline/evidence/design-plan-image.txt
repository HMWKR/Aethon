## 이미지 교체

```json
{"op":"replace_image","page":3,"node":"3n7","resource":{…}}
```

### 처리 경로 정하기

디자인에 넣을 이미지는 미리캔버스 요소 검색, 사용자 제공 이미지, 웹 이미지, 직접 그린 그림(SVG)으로 준비한다.
사용자가 이미지를 요청하지 않았어도 필요하면 웹 이미지와 그림을 쓴다. 핵심 이미지의 기준은 아래 "반영하지 못했을 때"에 있다.
아래 경로에서 사용자에게 알리는 문장은 사용자가 개발자가 아니므로 상황 한 줄과 다음에 할 일 한 가지로 말하고, 도구 이름 같은 말을 쓰지 않는다.
적힌 문장은 사용자 언어로 옮겨 쓰고 `<…>`는 대상으로 바꾼다.

이미지 자리마다 아래 순서로 출처를 정한다. 각 출처의 진행과 실패 처리는 해당 절에 있으며, 한 출처가 실패했다고 다음 출처를 자동으로 시도하지 않는다.
페이지 구성 뒤 아래 "배치와 plan 반영"에 따라 자리를 정하고 `replace_image`를 작성하는 것은 모든 출처가 같다.

1. **사용자 이미지.** 사용자가 디자인에 넣을 파일을 첨부했거나, 파일 경로나 이미지 주소를 줬거나, 미리캔버스에 올려 둔 이미지를 쓰자고 하면 그 이미지를 쓴다.
   첨부가 넣을 이미지인지 참고 자료인지는 안내서 `design/user-image`의 "넣을 이미지와 참고 자료"로 먼저 가른다. 아래 "사용자가 제공하거나 지정한 이미지"를 따른다.
2. **사용자 쪽 대상.** 요청의 주제가 사용자의 회사, 제품, 서비스, 팀원, 행사처럼 사용자 쪽의 특정 대상인데 그 이미지를 받지 못했으면
   웹에서 찾지 않고 검색 요소로 대신하지도 않는다. 남의 회사 로고나 모르는 사람의 사진이 들어가는 결과가 되기 때문이다.
   아래 "사용자 쪽 대상의 이미지가 없을 때"를 따른다.
3. **핵심 웹 이미지.** 요청의 주제 자체가 널리 알려진 실존 대상이면 웹에서 그 대상의 이미지를 찾는다. 유명한 밈, 제품, 인물, 로고, 작품, 영화나
   게임의 장면, 에펠탑처럼 그것이어야 알아보는 랜드마크가 해당한다. 비슷한 스톡 사진으로는 뜻이 통하지 않는 이미지다.
   여행지나 도시처럼 분위기 사진으로 충분한 장소, 주제와 관계없이 본문에 이름이 한 번 나오는 대상은 템플릿 선택 전에 미리 찾지 않는다.
   그런 자리의 웹 이미지는 아래 5번의 웹 우선 전략에서 자리를 정한 뒤 찾는다.
   웹 검색 도구가 있을 때만 찾는다. 아래 "핵심 웹 이미지"를 따른다. 웹 검색 도구가 없으면 같은 절의 실패 처리를 따른다.
4. **그림.** 절차, 흐름, 구조, 관계, 순서를 보여 줄 내용인데 그 구조를 표현한 템플릿 페이지가 없거나 맞지 않으면 SVG로 직접 그린다.
   사용자가 그림이나 도식으로 그려 달라고 했으면 맞는 템플릿 페이지가 있어도 그린다.
   판단 기준은 안내서 `design/plan-structure`의 "콘텐츠와 페이지 구성하기" 2단계에 있다. 아래 "직접 그릴 그림"을 따른다.
5. **일반 교체 이미지.** 템플릿과 페이지 구성을 정하고 위 1~4번 출처의 이미지를 넣을 자리를 정한 뒤, 안내서 `design/plan-structure`의 Photos 절의 제외 조건을 적용한다. 남은 자리는 아래 "일반 교체 이미지"를 따른다.

예를 들어 "해외 유명 밈 소개" 발표 자료는 밈마다 실제 밈 이미지나 GIF를 웹에서 찾아 넣는다. "우리 팀 소개" 발표 자료는 팀원 사진을 받기 전에는
만들지 않고 사진을 보내 달라고 한다. "서비스 구조 설명" 발표 자료는 템플릿에 구성도를 담을 페이지가 없으면 구성도와 요청 흐름을 그려 넣는다.
사용자가 다시 말해 주기를 기다리지 않는다.

이미지 등록 도구(`create_image_upload`, `register_image_from_url`)가 도구 목록에 없으면 사용자가 준 파일이나 URL, 웹 이미지, 그린 그림을 넣을 수 없고 미리캔버스 검색 요소만 쓸 수 있다.
사용자가 가져온 이미지가 요청의 핵심이면 검색 요소 또는 원본 유지 중 고르게 하고, 생성 후 편집 화면에서 직접 바꿀 수 있다고 알린다. 웹 이미지나 그림이 핵심이면 아래 "반영하지 못했을 때"를 따른다.
핵심이 아닌 사용자 이미지와 그림은 검색 요소로 진행하고 최종 응답에 반영하지 못한 내용을 알리되, 결과에 중요하지 않다면 반복하지 않는다. 다른 서버나 스크립트로 우회하지 않는다.

### 사용자가 제공하거나 지정한 이미지

- 넣을 이미지는 템플릿을 고르기 전에 등록하거나 고른다. 새 이미지인지 올려 둔 이미지인지, 등록과 고르기 방법, 직접 올리기가 막혔을 때의 대응은 안내서 `design/user-image`를 따른다.
- 안내서 `design/user-image`의 방법을 다 써도 등록하지 못했거나 넣을 자리가 없으면 아래 "반영하지 못했을 때"를 따른다.

### 사용자 쪽 대상의 이미지가 없을 때

- 템플릿을 고르기 전에 아래 문장으로 사용자 쪽 이미지 요청을 한 번 하고 현재 응답을 끝낸다.
- 사용자가 이미지를 보내면 위 "사용자가 제공하거나 지정한 이미지"로 진행한다.
- 사용자가 이미지 없이 진행하라고 하면 그 자리는 검색 요소로 채우되, 대상을 특정하는 사진(사람 얼굴, 제품 외형, 로고)은 넣지 않고 분위기 사진이나 배경으로 둔다.

사용자 쪽 이미지 요청: "<대상> 사진(또는 로고)이 있으면 넣어 드릴게요. 이 대화에 올려 주시거나 이미지 주소를 알려 주세요. 없으면 사진 없이 만들어 드릴까요?"

### 핵심 웹 이미지

위 3번 출처다. 후보의 확보, 확인, 등록과 등록 재시도는 안내서 `design/web-image`의 "핵심 웹 후보 확보와 확인"과 "등록과 재시도"를 따른다.

- 템플릿 선택 전에 실제 대상의 후보를 확보한다. 웹 이미지 후보 때문에 템플릿 검색어, 후보 비교와 선택 기준을 바꾸지 않는다. 페이지 구성 뒤 같은 안내서대로 등록과 확인을 마치고 넣을 자리를 정한다.
- 후보를 확보하지 못했거나 확인 결과 쓸 수 있는 후보가 없거나 등록하지 못하면 조용히 검색 요소로 채우지 않는다. 실패를 확인한 단계에서 아래 문장으로 웹 이미지 실패를 한 번 말하고 현재 응답을 끝낸다.
  사용자가 파일이나 이미지 주소를 보내면 위 "사용자가 제공하거나 지정한 이미지"로 진행한다. 대체나 생략은 사용자가 허용한 경우에만 그 방식으로 진행한다.
- 배치나 적용에 실패하면 아래 "반영하지 못했을 때"를 따른다.

웹 이미지 실패: "<대상> 이미지는 제가 가져올 수 없었어요. 파일이나 이미지 주소를 보내 주시면 넣어 드릴게요. 아니면 이미지 없이 만들어 드릴까요?"

### 직접 그릴 그림

위 4번 출처다. 템플릿 페이지는 그림체가 어울리고 사용자가 에디터에서 글자를 고칠 수 있으므로 먼저 쓴다.
그릴지는 템플릿 구조 정보(manifest)를 받고 페이지 구성을 정할 때 판단한다(안내서 `design/plan-structure`의 "콘텐츠와 페이지 구성하기" 2단계). 사용자가 그려 달라고 한 그림은 페이지 구성 때 바로 그린다.
그리기로 정했으면 넣을 자리를 정한 뒤 그 자리의 비율로 SVG를 직접 그려 `register_svg_image`에 본문을 넘긴다. 셸 유무와 관계없이 파일 업로드 경로로 보내지 않는다.

- 그리는 것의 예: 도식, 플로우차트, 시스템 구성도와 아키텍처, 조직도, 타임라인, 단계 흐름, 순환 구조, 마인드맵, 비교 매트릭스, 벤 다이어그램.
  목록에 없어도 기준은 같다. 글만으로는 관계나 순서가 한눈에 들어오지 않는 내용이다.
- 그리지 않는 것: 사진이나 사실적인 이미지(웹 이미지나 검색 요소), 수치 차트(안내서 `design/plan-data`의 차트), 문장(텍스트 슬롯),
  아이콘과 장식(검색 요소), 지도와 수식(텍스트 슬롯이나 검색 요소로 두고 최종 응답에 알린다).
- 작성 규칙
  - 원고나 사용자 요청에 있는 단계, 구성 요소, 관계만 그린다. 그림을 채우려고 원고에 없는 단계나 연결을 지어내지 않는다.
  - 루트 `<svg>`에 양수 `width`와 `height`, 같은 비율의 `viewBox`를 둔다. 비율은 넣을 자리의 `box` 비율에 맞춘다.
  - 외부 이미지, 외부 폰트, `<script>`, DTD(`<!DOCTYPE>`)를 쓰지 않는다. 한 파일 안에서 끝낸다.
  - 단순한 도형, 선, 화살표 위주로 그린다. 글자는 짧은 이름표 정도로만 넣고 `font-family`를 지정하지 않는다. 설명 문장은 템플릿의 텍스트 슬롯에 둔다.
  - 색은 템플릿 썸네일이나 manifest의 색에서 고른다. 배경은 투명으로 두어 템플릿 배경과 어울리게 한다.
  - 그림 하나는 1 MiB 이하다. 한 페이지에 핵심 그림 하나를 기본으로 한다.
- 배치: 넣을 자리는 manifest `photos[]`의 사진, 비트맵, 일러스트 자리 중 프레임이 없고 비율이 맞는 곳이다.
  알맞은 자리가 없는 페이지에는 그리지 않는다. 무엇을 그려 넣었는지 최종 응답에 알린다.
- 등록 결과의 처리와 실패했을 때의 수정 재시도는 도구 응답의 안내를 따른다. 그래도 등록하지 못하면 아래 "반영하지 못했을 때"를 따른다.

### 일반 교체 이미지

위 5번 출처다. 안내서 `design/plan-structure`의 Photos 절에서 정한 교체 대상만 처리한다. 이미지는 정한 콘텐츠에 맞춰 고르며, 사진 확보 여부를 이유로 콘텐츠를 바꾸거나 빼지 않는다. 페이지당 교체 개수 제한은 없다.
웹 처리와 요소 검색을 아래 순서로 나누어 진행한다. 같은 단계에서 서로 독립적인 자리의 호출은 함께 실행할 수 있지만, 앞선 결과에 따라 실행 여부가 달라지는 호출은 그 결과를 받은 뒤 수행한다.
교체 대상의 `photos[].kind`별 전략은 다음과 같다.

- `photo`: 아래 "웹 우선" 전략.
- `bitmap`: 아래 "웹 우선" 전략.
- `illust`: 웹 이미지를 시도하지 않고 아래 "미리캔버스 요소 검색"만 한다.
- 아이콘(`illust` 자리 중 원본 썸네일에서 픽토그램 같은 아이콘으로 보이는 것): `illust`와 같되 `kind`는 `ILLUST_ICON`으로 보낸다.

**웹 우선 전략**

1. 웹 우선 대상 전체를 안내서 `design/web-image`의 "일반 웹 후보 검색과 판정"에 따라 처리한다. 각 자리에서 등록과 확인을 마친 웹 후보를 선택하거나 아래 전환 조건이 성립하면 그 자리의 웹 처리를 마친다. 전체 대상의 웹 처리가 끝나기 전에는 `illust`와 아이콘을 포함해 요소 검색을 호출하지 않는다.
2. 웹 처리를 모두 마친 뒤, 전환 조건이 성립한 자리와 `illust`·아이콘을 모아 "미리캔버스 요소 검색"을 수행한다. 등록한 웹 이미지를 쓰기로 확정한 자리는 제외한다. 웹 우선 대상이 없으면 바로 요소 검색을 시작한다. 일반 교체용 웹 이미지의 전환은 사용자에게 선택을 묻지 않는다.
3. 적용 단계의 finding 처리는 아래 "배치와 plan 반영"에 있다.

**요소 검색으로 전환하는 조건**

- 그 자리의 검색에서 후보가 없거나, 찾은 후보에 안내서 `design/web-image`의 "직접 주소 확보"를 시도해도 주소를 얻지 못했거나, 후보 확인 결과 새 콘텐츠에 맞는 후보가 없다.
- 등록 전에는 볼 수 없어 등록한 후보를 등록 응답과 `get_my_image_previews`로도 확인하지 못했다.
- 웹 후보의 이미지 품질이 명확히 떨어져 사용할 만한 후보가 없거나, 등록 응답의 미리보기에서 중요한 피사체나 이미지 속 글자가 확연히 잘린다.
- 등록에 실패하고 안내서 `design/web-image`의 "등록과 재시도"에 따른 재시도도 실패했거나 재시도할 주소가 없다.

전환은 자리마다 실제 웹 시도 결과로 판단한다. 개별 검색 결과나 출처 페이지에 직접 주소가 없다는 이유로 전체 환경에서 주소 확보가 불가능하다고 판단하지 않는다. 속도나 비용, 다른 자리의 결과로 미시도 자리를 함께 전환하지 않는다.
전환을 결정한 자리는 웹 후보를 다시 검색하지 않는다.

### 미리캔버스 요소 검색

- 페이지 선택 전에 `get_template_page_previews`로 받은 원본 썸네일을 재사용한다. 복제한 페이지도 같은 원본 썸네일을 참고한다.
- 등록한 이미지를 쓰기로 확정한 자리는 제외하고, 위 "일반 교체 이미지"에서 요소 검색을 하기로 한 자리를 아래 두 단계로 검색한다.
  1. 처음 검색: manifest `photos[].resource.key`가 없거나, 원본 썸네일에서 실제 콘텐츠 없이 이미지 자리만 표시하는 더미 이미지로 보이는 대상은 `STYLE_SEARCH`로 검색한다. 나머지는 `MATCH_RECOMMEND`로 검색한다. 원본 key가 있으면 검색 방식과 관계없이 `originalResourceKey`에 전달한다. 두 방식의 호출은 같은 `searchMethod`끼리 `requestList`에 최대 5개씩 묶어 한 응답에 함께 보낸다.
  2. 재검색: `MATCH_RECOMMEND`에서 아래 후보 선택 기준에 맞는 후보를 고르지 못한 대상은 모두 `STYLE_SEARCH`로 한 번만 다시 검색한다. 검색 실패, 빈 결과, 후보 썸네일 부재로 선택하지 못한 경우도 포함한다. 처음 검색 결과를 모두 확인한 뒤 해당 대상을 `requestList`에 최대 5개씩 묶어 한 응답에 보낸다. keyword를 포함한 대상 값은 처음 검색과 같게 보낸다. 재검색 결과에서도 후보를 고르지 못했을 때 원본 유지로 확정한다.
- 교체 대상마다 해당 대상의 검색 결과에서 선택한다. 위 재검색 외에는 같은 대상을 요소 검색하지 않는다. 원본 페이지나 원본 이미지의 썸네일을 확인할 수 없어 검색에서 제외한 항목이 있어도, 나머지 대상의 검색은 생략하지 않는다.
- 선택한 템플릿의 공통 `templateKey`와 대상별 원본 `page`, `photos[].node`와 `kind`, `photos[].box`의 width와 height, `keyword`를 전달한다. 페이지 복제나 재정렬 후에도 검색에는 원본 페이지를, plan에는 실제 교체할 페이지와 노드를 지정한다.
  복제본은 원본과 같은 `page`와 `node`를 각자의 `keyword`로 같은 `requestList`에 함께 넣을 수 있다.
- `kind`는 `photos[].kind`를 쓴다. 아이콘은 위 "일반 교체 이미지"대로 `ILLUST_ICON`을 전달한다. manifest는 아이콘을 따로 구분하지 않는다.

**요소 검색어 생성**

- 특정 항목이나 사례에 딸린 이미지는 해당 항목이나 사례의 새 내용, 페이지 대표 이미지는 새로 구성할 페이지 전체 내용을 기준으로 검색어를 작성한다.
  눈에 띄는 단어 하나에 기대지 말고, 해당 내용이 전달하려는 의미를 이해한 뒤 이를 보여줄 대상이나 장면을 정한다.
  복제된 페이지에서도 각자 넣을 새 콘텐츠를 기준으로 판단한다.
- `keyword`에는 새 내용을 보여줄 대상/행동/형태를 간결하고 구체적으로 쓴다.
  수식어는 원하는 이미지의 모습을 구별하는 데 필요한 것만 남긴다. 예를 들어 지역 고유의 모습이 필요 없다면 `강원도 산` 대신 `산`으로 검색하되, 눈 덮인 모습이 필요하면 `눈 덮인 산`으로 검색한다.
- 사진/아이콘/일러스트 같은 요소 타입은 검색어에 넣지 않고 `kind`로 지정한다.

**요소 후보 선택**

- 그 자리의 새 콘텐츠를 나타내는 후보만 쓸 수 있다. 그런 후보가 없으면 고르지 않는다.
- 쓸 수 있는 후보 중에서 썸네일의 원본 이미지와 대상, 표현 방식, 구도를 견주어 새 콘텐츠에 가장 잘 맞는 것을 고른다. 자리의 톤은 쓸 수 있는 후보 사이의 우열을 가릴 때만 본다.
- 텍스트가 겹치는 자리는 기존 배치 구조와 어울리고 글자가 읽히는 후보를 고른다.
- 썸네일이 없는 후보는 선택하지 않으며, 이름이나 메타데이터만으로 이미지 내용을 단정하지 않는다.
- 비율이나 원본 크기만을 이유로 후보를 버리지 않는다.

검색과 후보 선택을 마치면 아래 "배치와 plan 반영"으로 진행한다.

### 배치와 plan 반영

**넣을 자리** (사용자 이미지, 핵심 웹 이미지, 그린 그림, GIF)

- 이미지와 글자가 겹치는 자리에서는 배치 후에도 글자를 읽을 수 있는지 확인한다.
- 사용자가 지정한 교체를 우선한다. 기존 로고나 장식도 사용자가 바꾸라고 지정하면 교체한다. 파일을 올렸다는 이유만으로 모든 이미지를 교체하지 않는다.
- 사용자 사진, 웹 이미지, 그림, GIF는 manifest `photos[]`에 있는 사진, 비트맵, 일러스트 자리에 종류와 관계없이 넣을 수 있다. 텍스트, 표, 선과 도형은 이미지 교체 대상이 아니다. 새 이미지 자리를 만들거나 페이지 전체를 재배치하지 않는다.
- 자리를 정하기 전에 이미지 내용을 본다. SVG가 아닌 이미지에 미리보기가 없으면 `get_my_image_previews`로 확인한다. SVG는 모델용 미리보기가 없으므로 직접 그린 그림은 그린 내용으로, 그 밖의 SVG는 파일 이름과 사용자 설명으로 판단한다. GIF 미리보기는 정지 이미지다.
- 사용자가 지정한 자리부터 고른다. 자리를 지정하지 않았으면 이미지의 용도, 주변 콘텐츠, 크기와 비율이 맞는 자리를 우선한다. 작은 장식 자리에 제품 사진을 억지로 넣지 않는다. GIF도 후보에 포함하되 로고와 장식은 기존 보존 규칙을 따르고, 정지 이미지로 바꾸지 않는다. 넣을 이미지가 자리보다 많으면 반영하지 못한 이미지를 알린다.
- 사용자 사진과 GIF는 기본으로 영역을 채운다(`fit: "cover"`). 로고, 제품과 글자가 든 이미지처럼 전체가 필요하면 프레임 없는 자리에서 `fit: "contain"`을 선택한다. SVG는 자르기를 지원하지 않아 전체 표시만 제공한다. 검색 요소에는 `fit`을 쓰지 않는다.
- 기존 프레임은 유지하며 해제하지 않는다. 프레임 안 전체 표시는 보장할 수 없으므로 SVG나 전체 표시가 필요한 이미지는 프레임 없는 자리를 고른다. 사용자가 지정한 자리와 충돌하면 제한을 알린다.
- `replace_image.resource`에는 등록 응답의 JSON을 그대로 쓴다. `fit`은 resource 안이 아니라 같은 연산의 필드다.
- 웹에서 찾아 등록한 이미지와 그린 그림도 같은 리소스 종류를 사용한다. 등록됐다는 사실만으로 사용자가 특정 자리나 장식의 교체를 지정했다고 판단하지 않는다.

**plan 반영**

- 쓸 수 있는 후보를 선택했으면 해당 대상의 `replace_image`를 `page_ops`에 추가하고, 응답의 `resource=` 뒤 JSON을 그대로 옮긴다. 값이나 크기를 지어내지 않는다.
- `page_ops`에서는 페이지 복제를 모두 마친 뒤 원본과 각 복제본의 `replace_image`를 배치한다.
- `node`는 manifest의 `photos[].node`를 그대로 쓴다. 복제한 페이지의 이미지는 `"page":"3#2","node":"3n7#2"`처럼 노드에도 같은 복제 접미사를 붙인다. 새 이미지 자리는 만들 수 없다.
- `STYLE_SEARCH`에서도 검색에 실패하거나 쓸 수 있는 후보가 없으면 교체 연산을 추가하지 않고 원본을 유지한다. 일반 교체 이미지의 후보 부족만으로 사용자에게 대체 방법을 묻고 멈추지 않고, 아래 "최종 대조"를 마친 뒤 생성한다.
- 미리캔버스 요소 검색으로 고른 이미지에 `image_missing`이나 `image_fit` finding이 오면, 이미 받은 요소 검색 결과나 그 자리에 등록해 둔 웹 후보(미리보기나 적용 단계에서 뺀 것은 제외) 가운데 쓸 수 있는 후보 중 자리 비율에 가까운 것으로 한 번만 바꾼다. 새로 검색하지 않으며, 처음 선택 실패 때의 `STYLE_SEARCH` 재검색도 여기에는 쓰지 않는다.
  바꿀 후보가 없거나 바꾼 뒤에도 `image_missing`이나 `image_fit`이 오면 해당 `replace_image` 연산을 제거해 원본을 유지한다.
- 일반 웹 이미지가 적용되지 않거나 `image_fit` finding이 오면 해당 `replace_image` 연산을 제거한다. 그 자리의 요소 검색 전이면 요소 검색으로 넘어가고, 이미 마쳤으면 원본을 유지한다.
  사용자 지정 이미지, 핵심 웹 이미지, 그린 그림의 finding은 아래 "반영하지 못했을 때"를 따른다.

### 반영하지 못했을 때

- 일반 교체용 웹 이미지의 적용 실패와 잘림 처리는 위 "배치와 plan 반영"을 따른다. 서버가 사용자 이미지라고 표시해도 모델이 자동 선택한 일반 웹 후보에는 그 규칙을 적용한다.
- 사용자 지정 이미지, 핵심 웹 이미지, 그린 그림에 잘림 경고가 오면 프레임 없는 자리에서 전체 표시로 바꾸거나 다른 기존 이미지 자리를 찾는다. 원본을 조용히 유지하거나 검색 이미지로 대신하지 않는다. 전체 표시의 여백 경고는 의도한 여백인지와 이미지가 너무 작지 않은지 판단한다. 필요하면 비율이 맞는 자리를 고른다.
- 핵심 이미지는 사용자가 필수로 지정한 이미지나 요청의 대상 자체인 이미지다. 단순 참고 자료나 모든 첨부를 일괄적으로 핵심으로 보지 않는다.
- 등록이나 배치에 실패한 이미지가 요청의 핵심이면 그 이미지를 뺀 결과를 완성본으로 저장하지 않는다. 실패 이유를 알리고, 사용자가 대체나 생략을 허용한 경우에만 그 방식으로 진행한다.
- 핵심이 아닌 일부 이미지만 넣지 못한 경우에는 나머지로 진행할 수 있다. 최종 응답에 반영하지 못한 이미지와 이유를 알린다.

### 최종 대조

- 이미지 처리의 `notes`는 반영하지 못한 요구나 최종 결과에 남은 오류·제한이 있을 때 해당 페이지와 node, 이유를 간결하게 적는다. 처리 결과가 바뀌면 기존 기록도 최종 plan에 맞게 갱신한다.
- 생성 전에 사용할 페이지(복제본 포함)의 `photos[]`, 검색과 확인 결과, 최종 plan을 대조해 각 항목의 검색 제외, 교체 또는 원본 유지 처리가 빠짐없이 이루어졌는지 확인한다.
  일반 교체 이미지 중 웹 우선 대상은 웹 시도, 요소 검색 전환 사유와 후보 확인 결과를 대조한다. 기존 검색 결과와 등록한 `resource`를 재사용하며, 최초 웹 시도를 포함해 빠뜨린 절차만 마친다. 해당 자리에서 탈락한 후보의 `replace_image`는 제거하고, 쓸 후보가 없으면 원본을 유지한다.
  위 "미리캔버스 요소 검색"의 재검색 대상에 `STYLE_SEARCH` 누락이 있으면 해당 대상만 재검색한다. 등록한 이미지를 쓰기로 확정한 자리는 제외한다.
- 최종 결과에는 이미지 관련 사용자 요구를 반영하지 못한 부분이나 결과 이해에 중요한 제한만 설명한다. 도구가 전달하지 않은 서버 장애나 권한 오류를 추정해 확정하지 않는다.
