## create_design 호출과 오류 처리

완성한 `plan`은 사용자에게 출력하는 대신 `create_design`의 `plan` 인자로 전달한다.

- 선택한 템플릿의 `templateKey`와 같은 값을 사용한다.
- `title`에는 사용자가 만들려는 디자인을 요약한 한 줄을 넣는다.

응답의 `findings`는 `plan` 적용 리포트다. 항목마다 처리 방향을 나타내는 `severity`와 분류인 `code`,
무엇을 어떻게 고칠지 알려주는 `message`가 있고, `plan`에서 위치를 특정할 수 있는 항목에는 JSON
Pointer인 `path`(예: `/page_ops/1`)가 있다.

- `error`: 그대로 저장하면 깨진 산출물이 되는 결정론적 결함이다. 판단 대상이 아니므로 `plan`을 고쳐
  0건을 만든다. `force`를 생략한 통상 호출에서는 하나라도 있으면 디자인이 저장되지 않는다.
  `unresolved`, `coverage`, `display`, `expose`, `hole`, `keep`, `keep_heavy`, `chart_stale`, `runjoin`,
  `linebreak`, `lint`, `fit_floor`, `fixed_text`, `running`, `dup_heavy`, `title_small`이 여기에 속한다.
- `warning`: 레이아웃이나 내용 판단이 필요한 항목이다. 저장을 막지 않는다. `dup`, `grow`, `grow_overlap`, `list_overflow`, `orphan`,
  `fit_small`, `role`, `squeeze`, `drop`, `scope`, `layout_repeat`, `group_partial`, `chart_pruned`, `chart_scale`,
  `chart_zero_series`, `chart_label_collision`, `table_overlap`, `table_cell_contrast`, `table_cell_overflow`, `series_text`, `recolor_warn`, `image_missing`, `image_fit`, `body_fit`이 여기에 속한다.
- `info`: 서버가 자동으로 처리한 내역이다. 차트는 안내서 `design/plan-data`의 "자동 보정과 진단"을 따른다.

슬롯마다 생기는 내역(`expose`와 `fit` 같은 자동 처리)은 `code` 하나에 한 항목으로 접혀 있고, 슬롯
목록은 그 항목의 `detail`에 있다. `expose`의 `detail.byPage`는 빈값으로 지워진 슬롯 id를 템플릿
페이지별로 묶은 것이므로, 페이지를 `delete`할지 슬롯을 `keep`할지 정할 때 읽는다.

응답 텍스트는 `severity`로 묶여 있고 `error`는 전부 실리지만, `warning`과 `info`는 `code`마다 앞
몇 건만 실린다. 줄어든 항목까지 확인해야 하면 `findings`를 읽는다.

`saved`가 `false`이면 `severity`가 `error`인 항목을 모두 `plan`에 반영한 뒤 다시 호출한다. 항목은
한꺼번에 반영한다.

- `unresolved`: 존재하지 않는 슬롯을 가리킨 것이다. `path`가 `replacements` 안의 자리(예:
  `/replacements/2/n8/1`은 페이지 키 `"2"` → 노드 키 `"n8"` → 배열 1번째)를 가리키므로 그 자리의 키를
  manifest의 노드 식별자로 바로잡는다. 값 자리에 슬롯 id를 써 넣지 않는다. `place_block`으로 자리를 내주고
  지워진 노드의 슬롯이면 그 노드 키를 지운다. 배열의 한 런만 지울 때는 원소를 빼지 말고 `null`로 둔다
  (원소를 빼면 뒤 런의 번호가 당겨진다).
- `coverage`: 원고 의미 단위마다 유효한 최종 페이지 라벨을 `at`으로 지정하거나, 제외 이유를 `drop`으로
  구체적으로 작성한다. `at`과 `drop`이 둘 다 없는 항목은 별도 메시지로 알려 준다. `path`가
  `/sources/<i>`이면 그 원고 항목의 신고가 없는 것이므로 `coverage`에 항목을 추가한다. `sources`에서
  항목을 지우는 것은 해결이 아니다.
- `display`: `display_copy` 항목이 규칙에 어긋난다. `message` 앞의 사유(줄 수, 글자 수, 영문 여부,
  `semantic_slots`, 슬롯 중복)를 보고 항목을 다시 쓴다. `path`가 `/display_copy/<i>`이면 그 항목이
  대상이다. `path`가 없으면 `replacements`로 조형 슬롯에 한글을 넣은 것이므로, 그 슬롯을
  `replacements`에서 지우고(배열의 한 런이면 `null`로 둔다) `display_copy`로 옮긴다. `display_applied` info는 배분이 끝난 내역이라 손볼
  것이 없다.
- `expose`: 교체도 `keep`도 하지 않은 슬롯이 빈값으로 지워졌다. `detail.byPage`를 보고 `replacements`로
  채우거나, 범용 라벨이면 `keep`하고, 페이지째 필요 없으면 `delete`한다.
- `hole`: 지운 자리가 비어 있다. 그 자리에 표·차트를 넣을 계획이면 `table_create`·`chart_create`의 `box`를
  메시지의 영역에 맞춰 덮는다. 그 밖에는 실제 데이터로 채우거나(`chart_set_data`, `add_nodes`), 남은 요소를
  재배치하거나(`move_nodes`, `set_group_count`, `align_nodes`), 페이지를 `delete`한다. 새 표·차트를 빼는 것은 해결이 아니다.
- `keep`: 없는 식별자를 `keep`했거나(manifest의 슬롯 식별자를 확인한다), 예시 수치·문장·자리표시 문구를
  `keep`한 것이다(콘텐츠로 교체한다).
- `keep_heavy`: 페이지가 사실상 템플릿 원본이다. 콘텐츠로 채우거나 페이지를 `delete`한다.
- `chart_stale`: 차트 위 라벨과 데이터가 불일치한다. 안내서 `design/plan-data`의 "자동 보정과 진단"을 따른다.
- `runjoin`: 같은 줄의 다음 런과 공백 없이 붙는다. 원본처럼 경계 공백이나 구분자를 유지한다. 조사로 시작하는
  런을 붙여 쓴 것은 이 오류가 아니므로 조사 앞에 공백을 넣지 않는다.
- `linebreak`: 줄바꿈 뒤가 구두점으로 시작한다. 구두점을 앞 줄 끝으로 옮긴다.
- `lint`: 텍스트가 캔버스를 벗어나거나 다른 요소와 겹친다. 텍스트를 줄이거나 `move_nodes`로 자리를
  옮긴다. `fontSize`를 `plan`에서 지정하지 않는다.
- `table_overlap`: 새 표와 주변 요소의 경계가 겹친다. 안내서 `design/plan-data`의 "표 영역 확보와 묶음 이동"에 따라 검토·수정한다.
- `table_cell_contrast`: 지정한 칸 글자색이 칸 배경과 대비가 낮다. 사용자가 정한 색이면 그대로 두고, 아니면 `text_color`를 바꾸거나 생략한다.
- `table_cell_overflow`: 표 칸의 글이 행 높이를 넘쳐 잘린다. 서버는 행을 늘릴 여유가 없고 글자도 하한까지 줄인 상태다.
  `message`의 칸마다 "들어가는 줄 수" 안으로 문구를 줄이거나 `table_delete_row`로 행을 줄이고, 그래도 안 되면 안내서 `design/plan-data`의
  "표 영역 확보와 묶음 이동"에 따라 표 아래 요소를 옮기거나 다른 페이지를 쓴다. 넘친 글을 지우는 것은 해결이 아니다.
- `fit_floor`: 축소 한계에 도달했다. 안내서 `design/plan-text`의 "공간이 부족할 때 plan 수정"에 따라 문구를 조정하거나 페이지를 복제해 나눈다.
- `fixed_text`: 곡선 텍스트는 원문 글자 수 이내의 한 줄로 쓴다. 장식 글자는 원문과 정확히 같은
  글자 수로 쓰거나 원문을 `keep`한다. 두 종류 모두 줄바꿈을 넣지 않는다. 허용 글자 수는 `message`를 따른다.
- `running`: 여러 페이지의 같은 자리에 반복되는 라벨에 서로 다른 값을 넣었다. 한 슬롯에만 값을
  지정하고 나머지 슬롯의 교체 값을 지운다. 서버가 같은 값을 나머지 페이지에 복사한다.
- `dup_heavy`: 한 페이지에 같은 문구가 여러 쌍 중복 배치됐다. `slotHints`의 페이지 제목과 부제 표시를
  확인하고, 같은 문구는 한 곳에만 넣도록 각 슬롯의 내용을 고친다.
- `title_small`: 페이지 제목이 지나치게 축소됐다. 제목을 짧게 쓰거나 수식어를 부제 슬롯으로 옮긴다.
- `shadow_text`: 원본에서 같은 문구가 겹쳐 있던 그림자 제목 쌍에 다른 문구를 넣었다. 서버가 본체의 문구로 맞췄으므로
  그림자에 넣으려던 내용은 다른 슬롯에 두고, 두 슬롯에는 같은 문구를 넣는다.
- `plan_input`, `bad_request`와 `page_ops`나 `recolor`의 입력 거절은 `path`와 `message`에 따라
  요청을 고친다. 입력 거절은 `force`로 우회할 수 없다.
- 그 밖의 `code`는 `severity`, `path`, `message`를 확인해 처리한다. 알 수 없는 오류를 입력 거절로
  단정하거나 `force`로 우회할 수 있다고 가정하지 않는다.
- 수정해도 풀리지 않는 `error`만 남고 응답이 허용하면, `force: true`로 저장한다.
  남은 항목은 `notes`에 적고 결과 링크와 함께 화면 기준으로 설명한다. `coverage`와 입력 거절은 우회할 수 없다.
  단, 텍스트 공간 부족(`fit_floor` 등)이나 겹침·잘림은 응답이 `force`를 안내해도 안내서 `design/plan-text`의 "공간이 부족할 때 plan 수정"을 우선한다.

수정 후에도 같은 `code`의 `error`가 반복되면 같은 수정을 되풀이하지 않는다. 위 규칙에 따라 저장하거나,
저장할 수 없으면 막힌 이유를 사용자에게 알린다.

`saved`가 `true`이면 다시 호출하지 않는다. 응답 안내에 따라 결과 링크를 사용자에게 전달하고, 결과
이해에 중요한 `warning` 항목이나 `notes`, 반영되지 않은 항목이 있으면 함께 설명한다.

저장 후 수정 요청은 같은 `templateKey`와 직전 `plan`에 반영해 `create_design`으로 새 디자인을 저장하고 새 링크를 안내한다.
plan으로 표현할 수 없는 수정만 편집 화면을 안내한다.

### 고친 부분만 다시 보내기

`saved`가 `false`인 `create_design` 응답과 `check_design_plan` 응답에는, 서버가 그 `plan`을 보관했으면 참조
`planRef`가 실린다. 그 뒤의 호출(오류를 고친 재호출, 재검증, 검증을 마친 `create_design`)에는 `plan` 대신
직전 응답의 `planRef`를 보내고, 고친 부분만 `planPatch`에 담는다. 응답마다 그때까지 고친 내용을 합친 `plan`이
새 `planRef`로 보관되므로 이전 `planRef`에 patch를 쓰면 그 뒤에 고친 내용이 빠진다. 고친 것이 없으면 `planPatch`를 뺀다.
서버가 보관한 `plan`에 `planPatch`를 적용한 뒤 처음 보낸 `plan`과 같은 검사와 적용을 거치므로 결과는
`plan` 전체를 다시 보낸 것과 같고, 교체 텍스트 수십 개가 든 `plan`을 다시 쓰는 것보다 훨씬 짧다.
`pages`를 바꿔 `prepare_design_plan`을 다시 받는 것처럼 `plan`을 새로 쓸 때는 `plan` 전체를 보낸다.

`planPatch`의 형식(세 연산, `path`의 표기)은 `create_design`의 인자 설명에 있다. 예:

```json
{"templateKey": "964875", "title": "…", "planRef": "p-3f9a1c2b7d4e5f6a7b8c9d0e",
 "planPatch": [
   {"op": "replace", "path": "/replacements/3/n1", "value": "상반기 문의 61,200건"},
   {"op": "replace", "path": "/replacements/2/n8/1", "value": "둘째 런"},
   {"op": "remove",  "path": "/page_ops/5"},
   {"op": "add",     "path": "/keep/-", "value": "0n1:0"},
   {"op": "add",     "path": "/coverage/-", "value": {"src": "가격", "drop": "가격 수치가 없어 임의로 쓸 수 없어서 제외함"}}]}
```

- 값을 고치는 finding은 그 `path`에 `replace`한다. `unresolved`처럼 키가 틀린 finding은 그 키를
  `remove`하고, 필요하면 맞는 노드 키에 `add`한다. 이미 있는 슬롯에 슬롯 id 키(`/replacements/3n1:0`)로
  다른 값을 `add`하면 같은 슬롯이 두 번 지정되어 거절된다.
- 연산은 순서대로 적용되고, 각 `path`는 앞 연산까지 반영된 상태를 가리킨다. 같은 배열에서 여러 항목을
  지우거나 끼울 때는 뒤 인덱스부터 적으면 보관된 `plan`의 인덱스를 그대로 쓸 수 있다. 런 하나를 지울
  때는 위 `unresolved`대로 `remove`하지 않고 그 자리를 `null`로 `replace`한다.
- `page_ops`는 배열 순서대로 적용되므로 연산을 `/page_ops/-`로 끝에 붙이면 순서 규칙이 깨질 수 있다.
  차트 연산처럼 자리가 정해진 연산은 안내서 `design/plan-data`의 "적용 순서"와 안내서 `design/plan-structure`의 "다른 페이지의 블록 배치하기"가 정한 인덱스에 `add`한다. 차트
  타입을 다시 바꿀 때는 기존 `chart_set_type`을 `replace`한다 — 그 자리가 이미 규칙에 맞고 타입 연산이
  둘 남지 않는다.
- 응답에 `planRef`가 없으면(서버가 보관하지 못함) 그때까지 고친 내용을 모두 반영한 `plan` 전체를
  `plan` 인자로 보낸다. `planRef`나 `planPatch`가 거절되면 오류 문장의 안내를 따른다.

## plan만 검증하기

`check_design_plan`에는 저장할 최종 `templateKey`와 `plan`을 전달하고(재검증이면 "고친 부분만 다시 보내기"대로
`planRef`와 `planPatch`) `findings`를 아래처럼 처리한다.

`valid=true`는 차단 오류가 없다는 뜻이며 표·차트 전환 완료를 보장하지 않는다.
오류 수정 후에도 남은 `series_text`를 다시 확인한다. 아래의 명시적 저장 승인 예외를 제외하면,
필요한 전환이나 근거 있는 예외 처리가 끝나지 않은 상태에서 `create_design`으로 넘어가지 않는다.

| 검증 결과 | 다음 행동 |
|---|---|
| `error` 있음 | 오류 대응 규칙대로 한꺼번에 수정 |
| 텍스트 공간 부족 경고 또는 화면에서 텍스트 겹침·잘림 확인 | 안내서 `design/plan-text`의 "공간이 부족할 때 plan 수정" 적용 |
| `series_text` 있음 / 원고와 plan의 수치 묶음 대응이 누락됨 | 안내서 `design/plan-data`의 "데이터로 표·차트 새로 만들기"에 따라 각 경고의 전환·예외 처리를 확인하고 수치 묶음별 실제 배치 위치와 전체 값을 대조. 경고 소거만으로 완료하지 않음 |
| `table_overlap` 또는 화면에서 표와 주변 요소의 충돌 확인 | 안내서 `design/plan-data`의 "표 영역 확보와 묶음 이동"에 따라 검토·수정. 경고만으로 실제 글자 가림을 단정하지 않음 |
| `chart_label_collision` 또는 차트 시각 오류 확인 | 진단의 `detail.hits` 또는 화면의 문제 위치를 근거로 아래 차트 대응 순서 적용 |
| `chart_placement` 또는 화면에서 새 차트가 한쪽에 치우치거나 띠에 붙음 | 안내서 `design/plan-data`의 "데이터로 표·차트 새로 만들기"의 `box` 기준으로 폭·간격을 고치거나 본문 페이지로 옮김. 장식 글자 옆 빈자리를 채우려고 차트를 키우지 않음 |
| plan 수정함 | 수정한 최종 plan 재검증. 동일 plan 반복 검증 금지 |
| error·확인된 시각 오류 없고 데이터 묶음 대응 확인 완료 | 다른 warning 반영 여부를 판단하고 검증 응답의 `planRef`(없으면 검증한 plan 전체)로 `create_design`. 화면 미확인은 시각 통과로 보지 않음 |
| 수정해도 같은 시각 오류가 남음 / 데이터 보존·배치의 적용 가능한 대안 없음 | 자동 수정을 멈추고 위치·추정 한계·대안을 설명하여 사용자 결정 확인. 남은 `error`가 텍스트 공간 부족이나 겹침·잘림(`lint`, `fit_floor` 등)이 아니면 묻지 않고 `create_design`의 `force` 규칙을 따름 |
| 남은 문제를 알고 저장하도록 승인받음 | `notes`에 기록하고 최종 plan 검증 후 저장. 같은 결정 재질문 금지. warning만 있으면 `force` 불필요 |
| 이미 `saved=true` | 재생성하지 않고 응답 안내에 따라 결과와 남은 검토 사항 안내 |

차트 시각 오류는 다음 순서에서 적용 가능한 방법으로 수정하고, 해결되면 멈춘다.

1. 현재 타입에서 지원되는 `label_position`과 배치를 조정한다. 새 차트는 생성 연산의 `box`를 조정한다.
   주변 공간이 부족하면 안내서 `design/plan-data`의 "표 영역 확보와 묶음 이동"의 순서로 다른 적합한 페이지까지 검토한다.
2. 충돌이 남으면 다른 원본 차트 또는 `chart_create`로 계열을 나눈다. 위 데이터 보존·배치 기준을 지킨다.
3. 그래도 해결되지 않으면 안내서 `design/plan-data`의 "타입 선택"에서 같은 전달 목적을 만족하는 대체 타입을 검토한다.
   사용자 타입 지정·유지 요청이 있으면 임의로 바꾸지 않는다. 표 전환은 값 조회·속성 대조 등 표 선택 조건에 맞을 때만 한다.
4. 대안이 없으면 위 표의 사용자 결정 확인 절차를 따른다.

전환 plan은 원본 기준으로 기존 타입 연산을 교체하고 안내서 `design/plan-data`의 "적용 순서"를 따른다. `label_position`·축 옵션은 최종 타입 제약에 맞춰
정리하며 연산을 중복 추가하지 않는다. 명시한 축 범위와 충돌하면 임의로 삭제하지 않고 대안에 대한 사용자 결정을 확인한다.
저장 후 화면에서 처음 발견한 문제는 위치와 대안을 알리고, 별도 요청 없이 재생성하지 않는다.

`check_design_plan`에는 `force`가 없다. 해결 불가능한 error의 저장은 위 `force` 규칙을 따른다.
