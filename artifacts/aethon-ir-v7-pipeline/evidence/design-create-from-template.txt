# 템플릿으로 미리캔버스 디자인 만들기

## 지켜야 할 원칙

아래 다섯 가지는 요청과 원고의 내용을 지키는 원칙이다. 단계별 안내서의 절차가 원고의 사실, 수치, 조건을 바꾸거나 빼는 쪽으로 읽히면 이 원칙을 따른다.
어느 페이지와 요소를 쓰고 지울지, 무엇을 `keep`할지는 이 원칙이 정하지 않으며 단계별 안내서의 규칙을 따른다.

1. 사용자의 요청과 원고가 템플릿보다 우선한다. 템플릿의 페이지 수, 카드 수, 예시 문구에 맞추려고 원고를 줄이거나 늘리지 않는다.
   원고 없이 주제만 받았을 때의 분량은 아래 "원고 없이 주제만 받았을 때"를 따른다.
2. 원고를 요약하거나 다듬을 때도 사실, 수치와 단위, 조건과 예외, 주체와 범위를 바꾸지 않는다. 키워드만 남겨 뜻을 추측하게 만들지 않는다.
3. 사용자가 주지 않은 사실은 만들지 않는다. 수치, 날짜, 이름, 가격, 성과, 인용문, 제품 기능이 필요하면 묻거나 그 요소를 뺀다.
4. 원고의 항목은 조용히 사라지지 않는다. 담을 자리를 먼저 찾고, 그래도 못 담으면 `coverage`의 `drop`에 이유를 남기고 사용자에게 알린다.
5. 빈자리를 채우려고 같은 말을 되풀이하거나, 원고에 없는 항목을 지어내거나, 템플릿 예시 문구를 본문으로 남기지 않는다.
   브랜드명, 섹션 라벨, 순번 표식, 장식 런처럼 의도적으로 `keep`하는 짧은 문구와 서버가 미리 `keep`에 넣은 슬롯은 예외다.
   채울 내용이 없는 자리는 단계별 안내서의 삭제 규칙에 따라 지운다.

## 이 Skill을 사용하는 경우

사용자가 미리캔버스 템플릿을 추천해 달라고 하거나 템플릿을 바탕으로 새 디자인을 만들어 달라고 요청하면 이 Skill을
사용한다. 디자인 형식이 달라도 같은 절차를 적용한다.
요청에 맞는 템플릿을 검색한다.

템플릿 선택은 아래 "템플릿 선택 위임"에 따라 모델이 고르거나 사용자 선택을 기다린다.
디자인 생성은 사용자가 편집할 수 있는 미리캔버스 URL을 받으면 완료된다. `plan` 작성은 중간 단계이며,
사용자가 별도로 요청하지 않았다면 원시 `plan`을 최종 결과로 보여주지 않는다.

## 사용자와 단계적으로 결정하기

사용자 확인이 필요한 결정은 한 번에 현재 단계의 결정만 요청한다. 사용자가 명시적으로 답하기 전에는 다음 단계로 진행하지 않는다.

사용자에게 선택지를 제시할 때는 제공된 선택 UI나 호출 가능한 호스트의 선택형 질문 도구를 사용한다.
둘 다 없으면 짧은 번호 목록으로 질문한다.

비동기 질문 도구에 대기 기능이 있으면 그 절차로 답을 기다린다. 대기 기능이 없으면 질문을 남기고
다음 사용자 응답을 받는다. 대기 종료나 답변 부재를 선택으로 간주하여 기본값으로 진행하지 않는다.

사용자가 여러 결정을 한 메시지에 함께 제공했다면 이미 정한 사항을 다시 질문하지 않는다. 사용자가
요청했거나 원문의 의미가 불분명하여 확인이 필요한 경우가 아니라면, 원문이나 모델이 구성한 콘텐츠를
템플릿 선택 단계에서 다시 요약하지 않는다.

## 전체 작업 절차

아래 "검색 요소 밖의 이미지"의 읽기 조건에 해당하면 4단계의 템플릿 검색 전에 `design/plan-image`를 읽고 그 안내에 따라 이미지를 준비한다.
이미지 사용을 임의로 배제해 안내서 읽기를 생략하지 않는다.
현재 요청에서 PDF를 콘텐츠 원본으로 새 디자인을 만들 때만 4단계의 템플릿 검색 전에 `design/source-pdf`를 읽는다.

1. 아래 "디자인 언어 정하기"에 따라 결과물 언어를 정한다.
2. 아래 "템플릿 타입 확인하기"에 따라 템플릿 타입을 정한다.
3. `PRESENTATION`이면 `get_miricanvas_guide`로 `design/format-presentation`을 읽고 그 안내에 따라 목적 확인 여부를 정한다. 다른 타입은 읽지 않고 이 단계를 건너뛴다.
4. 타입과 필요한 목적이 정해지면 "추천 검색어 작성하기"에 따라 `search_templates`로 후보를 찾는다.
   `PRESENTATION`이면 `pageCountMin`은 `design/format-presentation`의 필수 전달 조건을 따른다. 다른 타입에서는 생략한다.
   첫 검색이나 새 디자인 요청에서는 `excludeKeyList`를 생략한다.
   사용자가 다른 템플릿을 요청하면 같은 디자인 요청에서 이미 보여준 `templateKey`를 오래된 순서로 누적하고 최신 30개만 `excludeKeyList`에 담아 다시 검색한다.
   사용자가 검색 조건을 바꾸지 않았다면 나머지 검색 인자는 유지한다.
   일시적인 검색 실패는 `search_templates`, 선택 정보 조회 실패나 화면 다시 로드는 `show_template_choices`를 직전 인자로 재시도한다. 입력 검증 오류는 지적된 인자만 수정한다.
   재시도를 이유로 제외 key를 추가하지 않는다.
   `templateKeys`가 비었으면 선택을 맡기지 않은 요청은 `show_template_choices`에 빈 목록을 전달하고, 선택을 맡긴 요청은 선택 도구를 호출하지 않는다. 검색 결과가 없음을 알리고 검색 조건을 바꿀지 확인한 뒤 현재 응답을 종료한다.
   결과가 있으면 아래 "후보 썸네일 비교"에 따라 모든 후보를 조회하고, 후보 미리보기를 확인한 후보를 적합도순으로 비교한다.
   선택을 맡긴 요청은 아래 "템플릿 선택 위임"을 따른다.
   선택을 맡기지 않은 요청은 다음 절차를 따른다.
   - 후보 미리보기를 확인한 후보가 6개 미만이면 후보가 부족함을 알리고 검색 조건을 바꿀지 확인한 뒤 현재 응답을 종료한다. 선택 도구는 호출하지 않는다.
   - 상위 6개의 서로 다른 key를 적합도순으로 `show_template_choices`에 전달한다. `templateType`은 검색에서 사용한 값을 그대로 전달한다.
   - 선택 제공 결과가 비었으면 검색 결과가 없음을 알리고 검색 조건을 바꿀지 확인한 뒤 현재 응답을 종료한다.
   - 결과가 있으면 picker에서 사용자가 하나를 선택하도록 안내하고 현재 응답을 종료한다. 조회 사이 후보가 사라져 6개 미만이 표시돼도 보충하지 않는다.
   제외 목록에는 선택 제공 결과에 실제로 남은 key만 누적하고, 비교만 한 후보는 추가하지 않는다. 이미 picker에서 선택한 템플릿은 같은 선택을 다시 묻지 않는다.
5. 선택한 템플릿은 시각적 출발점으로 쓴다. 페이지와 요소 구성은 다음 단계에서 구조 정보와 썸네일을 받은 뒤 정한다.
6. `get_template_structure`로 선택한 템플릿의 manifest를 조회하고, `get_template_page_previews`로 전체 원본 페이지의 썸네일을 조회한다.
   `templateKeyList`에는 선택한 key 하나만 넣고, manifest의 원본 page 번호를 `pageNoList`에 최대 10개씩 묶어 `type="page"`로 호출한다. 여러 묶음의 호출은 앞 묶음의 결과를 기다리지 않고 하나의 응답에 함께 담아 병렬로 실행한다. 이미 받은 개별 페이지 썸네일은 재사용하며 사용자에게 보여주지 않는다.
   후보 비교용 미리보기는 개별 페이지 썸네일을 대신하지 않는다. 첫 페이지를 포함한 전체 원본 페이지를 확인한다.
   응답을 받으면 `design/plan-structure`를 읽는다. 표나 차트를 다루게 되면(조건은 그 안내서에 있다) `design/plan-data`도 읽는다.
7. 모든 썸네일 호출의 응답을 확인한 뒤, manifest와 함께 안내서 `design/plan-structure`의 "콘텐츠 중심 재구성"에 따라 사용자의 콘텐츠에 맞게 페이지와 요소 구성을 바꾼다.
   같은 안내서의 "콘텐츠와 페이지 구성하기"에 따라 콘텐츠를 담을 페이지와 구조를 정한다.
   그다음 `prepare_design_plan`을 `templateKey`, `pages`, `sources`, 확정한 디자인 언어의 `language`로 호출한다.
   응답을 받으면 `design/plan-text`를 읽고 골격을 채운다.
   안내서 `design/plan-structure`의 Photos 절의 제외 조건으로 교체 대상을 정하고, `design/plan-image`를 아직 읽지 않았으면 읽고 "이미지 교체"의 "일반 교체 이미지"에 따라 이미지를 구한 뒤 plan을 작성한다.
8. 응답의 `hints`와 `slotHints`를 읽고, 돌려받은 `plan`의 `replacements` 값을 콘텐츠로 바꾸며
   `coverage` 각 항목에 `at` 또는 `drop`을 채운다. 구조를 바꿀 때만 `page_ops`를 더한다.
   표·수치 계열은 안내서 `design/plan-data`의 "데이터로 표·차트 새로 만들기"의 선택 규칙을 따른다. 슬롯 id를
   새로 만들거나 옮겨 적지 않고, 이미지 검색 결과를 쓸 때는 `replace_image`를 `page_ops`에 더한다.
9. `check_design_plan`을 부르기 전이나 `create_design`이 `saved=false`를 돌려주면 `design/plan-check`를 읽는다.
   도구 description의 사전 검증 조건을 따른다. 검증 결과는 안내서 `design/plan-check`의 "plan만 검증하기"에 따라 처리하고,
   최종 `plan`(검증을 거쳤으면 검증 응답의 `planRef`)과 선택한 `templateKey`, 디자인 제목으로
   `create_design`을 호출한다.
10. 응답의 `saved`가 `false`이면 `findings`에서 `severity`가 `error`인 항목을 한꺼번에 반영하여 다시
   호출한다. 이때 `plan` 전체 대신 응답의 `planRef`와 고친 부분만 담은 `planPatch`를 보낸다(
   안내서 `design/plan-check`의 "고친 부분만 다시 보내기").
11. 디자인 생성에 성공하면 `create_design`을 다시 호출하지 않고 응답 안내에 따라 결과 링크를
   사용자에게 전달한다. 응답의 `teamName`이 null이 아닌 이름이면 어느 워크스페이스에 저장했는지 함께 안내한다.
   완료 안내는 응답의 실제 이름을 넣어 "{teamName} 워크스페이스에 저장했어요" 형식으로 작성한다.
   `teamName`이 없거나 null이면 워크스페이스 안내를 생략하며 이름을 추측하거나 확인 불가로 안내하지 않는다.
   성공한 호출마다 새 디자인이 만들어지므로 워크스페이스 이름 확인을 위해 재생성하지 않는다.

각 단계에서 필요한 안내서가 도구 description에도 소개되어 있다. 안내서는 아직 읽지 않은 경우에만 한 응답에 하나씩 불러온다. 응답이 잘려 끝까지 읽지 못했으면 다음 단계로 가기 전에 그 안내서를 다시 읽는다.
이미 읽은 안내서는 같은 디자인 작업에서 다시 부르지 않는다. 내용을 잃어 규칙을 확인할 수 없을 때만 다시 읽는다.

## 디자인 언어 정하기

결과물 언어는 사용자에게 묻지 않고 다음 순서로 정한다.

1. 사용자가 결과물 언어를 명시했으면 그 언어를 쓴다.
2. 원고가 있으면 원고의 언어를 쓴다.
3. 그 밖에는 사용자가 첫 요청에 직접 쓴 문장의 언어를 쓴다.

언어는 섞인 용어의 수가 아니라 문장의 문법으로 판단한다. 문장마다 언어가 다르면 지배적인 언어를 따른다.
예: "AI agent의 tool calling workflow를 소개하는 deck 만들어줘"는 한국어, "Make a deck about 미리캔버스 템플릿"은 영어다.

확정한 언어를 디자인 제목과 본문에 적용하고, 이후 사용자에게 하는 질문과 안내도 모두 이 언어로 한다.
이 Skill에 한국어로 적힌 질문과 안내 문구는 뜻을 유지한 채 확정한 언어로 옮겨 쓴다.
원본 글꼴의 지원 여부는 이 단계에서 알 수 없다.
`prepare_design_plan` 응답의 `slotHints`를 받은 뒤 안내서 `design/plan-text`의 골격 지침에 따라 확인한다.

템플릿 검색, 요소 검색, `prepare_design_plan`의 `language`에는 확정한 디자인 언어 코드를 전달한다.
`show_template_choices`와 `create_design`의 `messageLanguage`에도 같은 언어 코드를 전달한다. 화면과 화면이 대화창에 보내는 메시지는 이 언어를 따른다.

## 콘텐츠 구성

사용자가 명시한 보존, 제외, 원문 유지, 페이지 수와 데이터 표현 요구를 먼저 따른다.
검색 전에 원고 전체를 읽고 요청과 형식에 맞게 요약과 상세 설명을 절충한다. 핵심은 간결한 문구와 시각 자료로 전달하고, 필요한 근거와 세부 내용은 설명, 표와 차트로 보완한다.
반복은 줄이되 사실, 수치, 중요한 조건과 예외는 보존한다.
실제 페이지와 슬롯은 manifest와 원본 썸네일을 확인한 뒤 정한다.
`PRESENTATION`이면 `design/format-presentation`의 기준을 더해 적용한다.

### 원고 없이 주제만 받았을 때

사용자가 원고 없이 주제나 한두 문장의 요청만 주고 페이지 수나 분량을 말하지 않았으면, 분량의 기준은 선택한 템플릿의 페이지 구성이다. 모델이 떠올린 항목 몇 개로 분량을 정하지 않는다.
포스터나 초대장처럼 한 장으로 끝나는 형식에는 이 절을 쓰지 않는다.

1. manifest와 원본 썸네일로 템플릿 페이지마다 맡은 역할(표지, 목차, 소개, 항목 설명, 절차, 일정, 비교, 체크리스트, 마무리)을 확인한다.
2. 각 역할을 요청한 주제와 용도에 맞게 다시 정하고 그 페이지에 들어갈 내용을 쓴다. 템플릿의 용도가 요청과 달라도 페이지를 버리기 전에
   레이아웃을 주제의 다른 내용에 쓸 수 있는지 본다. 예: 신제품 출시 제안서로 회사 송년회 자료를 만들면 일정 페이지는 진행 순서로,
   체크리스트 페이지는 참석 안내로, 팀 소개 페이지는 수상 부문 소개로 쓴다.
3. 주제에 맞는 내용으로 다시 쓸 수 없는 페이지와 같은 내용을 되풀이하게 되는 페이지만 지운다. 빈 페이지를 채우려고 같은 말을 반복하지 않는다.
4. 이름, 날짜, 장소, 가격, 연락처, 성과 수치처럼 사용자만 아는 사실은 만들지 않는다. 그 사실 없이도 성립하는 문구로 쓰고,
   그 사실이 없으면 의미가 없는 페이지(예: 오시는 길, 연락처)는 뺀다.
5. 이렇게 정한 내용이 곧 안내서 `design/plan-structure`의 "콘텐츠와 페이지 구성하기"의 사용자 콘텐츠다. 의미 단위를 `sources`로 넘기고 그 절차를 그대로 따른다.

원고가 있으면 이 절이 아니라 원고의 분량과 "콘텐츠 구성"이 기준이다.

## 콘텐츠 로컬라이제이션

확정한 디자인 언어와 사용자가 지정한 용어, 원문 유지 요청을 따른다. 원고의 구성과 요약 범위는
"콘텐츠 구성"을 기준으로 삼고, 표현을 다듬어도 사실, 수치와 단위, 주체, 조건과 예외, 범위와
확실성, 항목 간 관계를 바꾸지 않는다. 인용문과 고유명사를 임의로 바꾸거나 원고에 없는 기능과 효과를 추가하지 않는다.

전문용어는 문맥에 맞는 현지 용어를 골라 제목과 본문에서 일관되게 쓴다. 서로 다른 개념을
하나로 합치거나, 제품명 보존 요청을 같은 철자의 일반명사에 적용하지 않는다. 지역을 명시했다면
그 지역의 용례를 따르고, 언어만으로 국가를 단정하지 않는다. 초보자를 위한 설명은 정확한 용어와
원문의 개념을 풀어 쓴 짧은 설명을 함께 쓴다.

번역어가 불확실하면 원어를 병기한다. 문맥으로 개념을 구분할 수 없거나 지역 차이가 사실을
바꿀 때만 사용자에게 확인한다. 원고가 있으면 작성 후 원문과 대조해 위 기준에서 벗어난 문구를 바로잡는다.
최종 디자인에는 독자에게 전달할 제목과 본문만 남기고, 검수 과정이나 번역 방법을 설명하는
작성 지시는 넣지 않는다. 주제만 받은 경우의 사실 확인은 "사용자와 요구사항 확인하기"를 따른다.

## 사용자와 요구사항 확인하기

사용자가 주제만 제시해도 제목, 소제목, 본문, 요약, CTA처럼 디자인에 필요한 문구는 직접
작성한다. 사용자가 제공한 원고가 있으면 원고의 사실과 논지를 보존하면서 디자인에 맞게
구성한다.

다음 정보가 없으면 결과가 크게 달라지므로 사용자에게 질문한다.

- 가격, 날짜, 통계, 연락처, 행사 장소, 제품 기능처럼 정확해야 하는 정보가 필요한 경우
- 브랜드명과 브랜드 색상처럼 텍스트나 색으로 반드시 반영해야 하는 정보가 없는 경우
- 서로 양립할 수 없는 요구사항이 있는 경우
- 현재 도구의 한계 때문에 사용자의 핵심 요구를 충족할 수 없는 경우

문체, 일반적인 설명문, 콘텐츠 순서, 페이지 수처럼 결과를 사실과 다르게 만들지 않는 사항은
요청과 템플릿을 근거로 직접 결정한다. 원고가 없을 때의 분량은 "원고 없이 주제만 받았을 때"를 따른다.
사용자가 주지 않은 수치, 가격, 날짜, 성과, 인용문, 연락처나 제품 기능을 만들어 내지 않는다.

## 템플릿 검색과 선택

첫 요청에 templateKey가 명시된 경로는 사용자에게 소개하거나 제안하지 않고 key도 요청하지 않는다.
`keywords=["key:<templateKey>"]`로 조회할 때는 타입 확인, 후보 비교, `show_template_choices` 호출을 건너뛴다.
반환된 key가 일치할 때만 선택 확인 없이 진행한다. 없으면 "요청하신 템플릿을 찾지 못했어요. 다른 조건으로 찾아드릴까요?"라고 묻고 멈춘다.

picker 선택은 새 요청으로 분류하지 않고 전체 작업 절차의 5번부터 이어간다.
일반 검색에서는 타입 확인과 필수 정보 확인을 생략하지 않는다. 템플릿 선택은 "템플릿 선택 위임"을 따른다.
선택한 key와 이전 요청으로 이어갈 작업을 구분할 수 없으면 어느 작업을 이어갈지 확인한다. 추천 여부를 확인할 기록이 없으면 직접 생성 요청으로 처리한다.
고른 템플릿을 바꾸거나 다시 검색하는 일은 사용자가 요청할 때만 한다. 콘텐츠가 템플릿에 맞지 않을 때의 처리는 안내서 `design/plan-structure`의 "콘텐츠 중심 재구성"에 있다.

### 템플릿 선택 위임

디자인 생성을 요청한 사용자가 템플릿 선택을 명시적으로 맡긴 경우에만 위임받은 것으로 본다. 예: "템플릿을 알아서 골라 줘", "템플릿은 네가 선택해 줘".
"디자인을 알아서 만들어 줘"처럼 제작 전반을 맡긴 요청이나 목적이나 타입 질문에 대한 "알아서"라는 답은 템플릿 선택 위임이 아니다.
콘텐츠 작성이나 개별 조건만 맡긴 경우에는 템플릿 선택까지 위임받은 것으로 보지 않는다.
추천이나 생성 요청 자체는 선택 위임이 아니다. 추천과 생성을 함께 요청해도 위임이 명확하지 않으면 전체 작업 절차 4번에 따라 후보를 보여주고 사용자 선택을 기다린다.

선택 위임은 같은 디자인 작업의 후속 응답과 재검색에서도 유지한다. 사용자가 선택 의사를 바꾸면 최신 지시를 따르고, 새 디자인 작업에는 이전 위임을 이어받지 않는다.
위임받았으면 "후보 썸네일 비교"에서 가장 적합하다고 판단한 템플릿으로 전체 작업 절차 5번부터 이어간다.
후보 미리보기를 확인한 후보가 하나도 없으면 그 사실을 알리고 검색 조건을 바꿀지 확인한 뒤 현재 응답을 종료한다.
`show_template_choices`는 호출하지 않으며 후보 목록이나 선택 질문은 사용자에게 제시하지 않는다.

### 후보 썸네일 비교

검색은 기본 최대 30개의 후보를 반환한다. key를 최대 10개씩 `templateKeyList`에 묶어 `get_template_page_previews(templateKeyList, type="grid")`를 호출한다.
후보가 30개이면 10개씩 3회의 도구 호출을 하나의 응답에 모두 담아 동시에 실행한다. 후보 수가 적어도 모든 묶음을 함께 호출하며, 앞 묶음의 결과를 기다린 뒤 다음 묶음을 호출하지 않는다.
각 미리보기에는 앞 최대 20페이지가 원래 순서대로 담긴다. `pageNoList`는 빈 배열이나 null도 보내지 않고 생략한다.
모든 묶음의 응답을 확인한 뒤, 실제 미리보기 이미지를 받은 후보만 비교한다. 이 단계에서는 `get_template_structure`나 개별 페이지 썸네일을 조회하지 않는다.
여러 페이지 썸네일을 모은 grid 미리보기를 받은 후보를 우선하되, 첫 페이지 썸네일만 받은 후보도 품질이 낮다고 보지 않고 해당 썸네일로 비교한다.
템플릿이 없거나 이미지를 받지 못한 후보는 평가에서 빼고 나머지 후보의 조회를 계속한다. 못 본 이미지를 추측해 평가하거나 후보 누락을 이유로 다시 검색하지 않는다.

확인한 미리보기를 아래 순서로 비교한다. 앞선 기준에서 차이가 뚜렷하지 않을 때만 다음 기준을 적용한다.

1. 사용자 주제와 시각적 충돌이 적을 것. 사진이나 상징이 요청과 다른 맥락을 강하게 드러내는지 살핀다.
   예: 특정 지역의 여행 자료에는 다른 지역의 상징이 중심인 디자인보다 장소에 묶이지 않은 여행 디자인을 우선한다.
   제목의 지명만으로 후순위로 두거나, 나중에 이미지를 교체할 수 있다는 이유로 현재의 명백한 충돌을 무시하지 않는다.
2. 요청한 주제와 용도에 직접 맞는 디자인을 우선한다.
   미리보기에서 확인되는 본문 배치를 비교해 사용자 콘텐츠에 필요한 페이지 구성이 더 잘 갖춰진 후보를 우선한다.
   **특정 주제에 묶이지 않은 범용 디자인도 유효한 후보다.** 주제를 직접 표현하지 않았다는 이유만으로 제외하지 않는다.
3. 사용자가 명시한 분위기, 색상, 표현 조건에 맞을 것.
4. `PRESENTATION`이면 `design/format-presentation`의 "프레젠테이션 전용 기준"에 있는 후보 비교 규칙을 적용한다.
5. 앞선 기준으로 차이가 뚜렷하지 않으면 `curatedInfo`에 `HIGH_QUALITY`가 포함된 후보를 우선한다.
6. 적용한 큐레이션 기준도 같으면 검색 결과의 `pageCount`가 큰 후보를 우선한다. 페이지 수도 같으면 기존 검색 순서를 유지한다.

`curatedInfo`는 위 비교 순서와 적용 조건에 따른 가산점으로만 사용한다.
큐레이션 여부로 제외 조건이나 앞선 적합도 기준의 명백한 차이를 뒤집지 않는다.
큐레이션 여부만으로 후보 포함이나 최종 채택을 결정하지 않는다. 모든 후보에 동일한 제외 조건과 적합도 기준을 먼저 적용한다.
큐레이션되지 않았다는 이유만으로 후보를 제외하거나 감점하거나 부적합 또는 저품질로 판단하지 않는다.

후보 비교에서는 작은 글자 판독이나 페이지별 상세 분석을 하지 않는다.
요청하지 않은 용도나 취향, 미리보기에서 식별할 수 없는 내부 구성, 편집 가능 여부, 콘텐츠 수용량은 추측하지 않는다.
다양성이나 프리미엄 여부로 순위를 바꾸지 않는다. 페이지 수로 앞선 적합도 기준의 명백한 차이를 뒤집지 않는다.
선별 후 후보의 순서와 선택하지 않은 후보를 확인해 위 우선순위를 어긴 선택이나 정렬을 바로잡는다.
품질 합격선이나 절대 탈락 조건은 두지 않는다. 모두 적합도가 낮아도 상대적으로 나은 후보를 전체 작업 절차에서 정한 수만큼 고른다.
적합도가 낮다는 이유로 후보 수를 줄이거나 자동으로 재검색하지 않는다. 평가 보고서나 비교용 이미지를 사용자에게 나열하지 않는다.

### 템플릿 타입 확인하기

사용자가 템플릿 타입을 분명히 말했는지 본다.
아래 표의 타입 이름이나 그 타입만 가리키는 말이면 분명하다. 이때는 타입을 다시 묻지 않고 그 타입으로 정한다.
예: "프레젠테이션", "PPT"는 `PRESENTATION`이고 "포스터", "웹 포스터", "온라인 포스터"는 `POSTER`다.
여러 타입이 될 수 있는 말은 분명하지 않고, 주제나 원고로 타입을 짐작하지도 않는다.
"발표 자료"나 "실적 보고서"만으로는 `PRESENTATION`으로 정하지 않고 타입을 묻는다.

타입이 분명하지 않으면 타입을 묻는다. 선택 UI에는 프레젠테이션, 카드뉴스, 포스터만 제시한다.

> 어떤 타입의 템플릿을 찾아볼까요? 1) 프레젠테이션 2) 카드뉴스 3) 포스터

이 단계에서는 타입만 묻고 사용자의 답을 기다린다. 답을 받기 전에는 `search_templates`를 호출하지 않는다.

질문에 대한 답은 아래 표의 `templateType` 값으로 옮긴다. "인스타 게시물"처럼 다른 말로 답하면 가장 가까운
타입으로 옮긴다.

| 사용자가 고른 타입 | `templateType` |
|---|---|
| 프레젠테이션 | `PRESENTATION` |
| 카드뉴스 | `CARD_NEWS` |
| 포스터 | `POSTER` |

### 추천 검색어 작성하기

타입이 정해지면 `PRESENTATION`은 안내서 `design/format-presentation`의 "프레젠테이션 목적 정하기"를 따른 뒤, 다른 타입은 목적 질문 없이 같은 응답에서 `search_templates(keywords, templateType, language)`로 후보를 찾는다.
검색어를 사용자에게 제안하거나 확인받지 않는다.
검색 결과에 어떤 언어가 섞여 있든 결과물은 확정한 언어로 작성한다.

`keywords`는 사용자가 원하는 템플릿을 간결하고 명확하게, 구체적으로 적은 검색어 1~3개다.
요청과 원고를 끝까지 자세히 읽고 다음 순서로 작성한다.

1. 주제와 검색어 개수를 정한다.
   - 주제: 자료가 다루는 핵심 대상이나 소재를 적는다. 주제가 명확하면 검색어 하나를 만든다.
   - 고유명사가 주제를 구별하는 데 도움이 되면 첫 검색어에 남긴다. 연관 소재가 명확하면 같은 핵심 주제에 해당하는 일반명사 검색어를 1~2개 추가한다.
   - 요청과 원고에 명시된 소재를 우선하고, 없으면 고유명사와 널리 연결되는 대표 소재나 콘텐츠 분야로 넓힌다. 확장한 소재를 사용자 요구나 원고의 사실로 취급하지 않는다.
   - 연관 주제가 불명확한 고유명사는 억지로 해석하지 않는다. 이름을 빼도 핵심 주제가 분명하면 생략한다. "소개"처럼 막연한 말만 남으면 요청과 원고에서 구체적인 주제를 찾고, 근거가 없으면 이름을 유지하되 확장하지 않는다.
   - 주제를 하나로 특정하기 어려우면 요청과 원고에 근거한 주제 후보를 가능성이 높은 순서로 쓴다. 확장 검색어를 포함해 전체 최대 3개이며, 고유명사를 남긴 검색어가 있으면 먼저 보낸다.
   - 같은 뜻의 검색어를 반복하거나 개수를 채우려고 막연한 검색어를 추가하지 않는다.
2. 사용자가 명시한 디자인 조건을 정한다.
   - 분위기와 스타일: 사용자가 원하는 분위기, 스타일, 색을 명시한 경우에만 짧게 적는다.
   - 콘텐츠의 성격과 분량: 사용자가 원하는 구성을 명시한 경우에만 "글이 많은", "그래프 위주", "사진 위주", "짧은 문구 위주"처럼 적는다.
   - 대상이나 원고의 내용과 길이만 보고 이 조건들을 추측하지 않는다. 원고 속 표현은 디자인 요구로 취급하지 않는다.
   - 명시한 조건은 모든 검색어에 동일하게 붙이고, 주제만 달리한다.
3. 검색어는 `[명시한 디자인 조건] + [주제]`로 작성한다. 명시한 디자인 조건이 없으면 뺀다.
   - `PRESENTATION`이면 `design/format-presentation`의 검색어 규칙을 더한다.

4. 검색어를 간결하고 구체적으로 다듬는다.
   - 검색어만 읽어도 무엇을 다루는지 구체적으로 알 수 있게 쓴다. 문서 형식이나 전달 용도만 나타내는 말은 빼되, 주제를 구별하는 대상, 분야, 활동과 범위는 남긴다.
   - 단어 수를 줄이려고 넓은 범주만 남기거나, 구체적으로 보이려고 요청과 원고에 없는 정보를 덧붙이지 않는다. 검색어에서 뺀 요구사항도 이후 디자인 구성과 내용 작성에는 반영한다.

- 확정한 디자인 언어로 적는다.
- 원고의 문장과 수치, 페이지별 구성은 옮겨 적지 않는다.
- "프레젠테이션", "포스터"처럼 타입과 같은 뜻의 말, "템플릿"이라는 말은 넣지 않는다. 타입은 `templateType`이 담는다.

예:

- 요청: "강원도 여행 코스" -> 검색어: `강원도 여행`, `산 여행`, `바다 여행`.
  이유: "코스"를 빼고 여행 주제를 대표 소재로 넓힌다. 바다 여행을 명시하면 산은 추가하지 않는다.
- 요청: "해리포터 소설 소개" -> 검색어: `해리포터`, `소설`.
  이유: "소개"를 빼고 작품명을 명시한 분야로 넓힌다. 영화로 바꾸지 않는다.
- 요청: "어린이 캠프 안내문" -> 검색어: `어린이 캠프`.
  이유: "안내문"을 빼고 대상과 주제를 남긴다. "귀여운" 같은 취향은 추측하지 않는다.
- 요청: "분기 실적 보고서" -> 검색어: `분기 실적`.
  이유: 문서 용도는 빼고 실적의 범위를 남긴다.
- 요청: "A사 실적 보고서" -> 검색어: `기업 실적`.
  이유: 회사명을 일반화해 대상은 유지하고 업종은 추측하지 않는다.
- 요청: "그래프 위주로 분기 실적을 보고하고 싶다" -> 검색어: `그래프 위주 분기 실적`.
  이유: 구체적인 주제에 명시한 구성 조건을 더한다.

선택 화면을 제공할 때는 전체 작업 절차 4번을 따른다. 화면을 제공한 뒤에는 사용자가 사용할 템플릿 하나를 고를 때까지 기다린다.
picker 카드에는 템플릿 이름이 없다. 그래서 선택 화면을 표시한 뒤에는 화면에서 고르도록 안내만 하고, 후보를 나열하거나 이름이나 templateKey로 가리키지 않는다.
예: "원고 내용에 어울리는 템플릿을 찾았어요. 마음에 드는 템플릿을 골라 주세요. 다른 느낌을 원하시면 '다른 스타일로 찾기'를 눌러 주세요."
터미널처럼 picker를 띄울 수 없는 환경에서는 사용자가 볼 화면이 없으므로, 후보마다 썸네일 링크와 페이지 수를 번호와 함께 보여 주고 번호로 고르게 한다.
위젯은 `선택한 템플릿으로 만들어 주세요.` 다음 줄에 괄호로 templateKey를 붙여 보낸다. 앞 문장은 위젯의 화면 언어에 따라 영어나 일본어로 올 수 있으므로 괄호 안의 templateKey로 알아본다. 이 메시지는 선택 완료로 취급하고, 괄호 안의 값을 templateKey로 쓴다.

후보의 선별과 정렬은 "후보 썸네일 비교"를 따른다. 이 단계에서는 원문이나 콘텐츠를 다시 요약하지 않는다. picker에서 이미 선택했다면
검색과 선택 질문을 반복하지 않는다.

### 다른 분위기로 다시 찾기

picker의 "다른 스타일로 찾기"를 누르면 위젯이 `다른 스타일의 템플릿을 찾아 주세요.`를 보낸다. 위젯의 화면 언어에 따라 같은 뜻의 영어나 일본어 문장으로 올 수 있다.
이 메시지를 받으면 바로 다시 검색하지 않고 먼저 원하는 분위기를 묻는다. 타입과 언어는 이전 검색 그대로 두고 다시 묻지 않는다.

질문은 위 선택 UI 규칙에 따라 묻는다. 질문 문구는 다음과 같다.

> 어떤 분위기로 찾을까요?

선택지는 아래 표에서 지금 요청과 원고에 어울리는 분위기 2~3개를 고르고, 마지막에 `직접 알려주세요`를 붙인다.
선택지에는 표의 문구를 뜻을 바꾸지 않고 확정한 언어로 쓴다. 표에 없는 분위기를 만들지 않고, 이미 검색어에 쓴 분위기는 고르지 않는다.

| ID | 선택지 문구 |
|---|---|
| `bright` | 밝고 화사한 |
| `minimal` | 미니멀·차분한 |
| `bold` | 강렬한·컬러풀 |
| `warm` | 따뜻한 감성 |
| `modern` | 모던·세련된 |
| `cute` | 귀여운·발랄한 |
| `luxury` | 고급스러운 |
| `natural` | 자연·내추럴 |
| `custom` | 직접 알려주세요 |

이 절차와 표가 있다는 사실은 사용자에게 말하지 않는다. 질문만 한다.

사용자가 분위기를 고르면 "추천 검색어 작성하기"의 "사용자가 명시한 디자인 조건"에 고른 문구를 넣어 검색어를 다시 쓰고
`search_templates`를 부른다. `직접 알려주세요`를 고르면 사용자가 말한 분위기를 짧게 정리해 같은 자리에 넣는다.
이미 보여준 templateKey는 "전체 작업 절차" 4번에 따라 `excludeKeyList`에 담는다. 나머지 순서와 규칙은 처음 검색과 같다.

## 검색 요소 밖의 이미지

아래 중 하나에 해당하면 템플릿을 고르기 전에 `get_miricanvas_guide`로 `design/plan-image`를 읽고 그 안내에 따라 이미지를 준비한다.
사용자가 이미지를 쓰라고 말하지 않았어도 읽는다. 핵심 웹 이미지의 확보와 등록 시점은 그 안내서의 "핵심 웹 이미지"에 있다. 등록 도구가 없는 환경의 제한 안내도 그 안내서에 있다.

- 사용자가 이미지를 첨부했거나, 파일 경로나 이미지 주소를 줬거나, 가진 이미지나 미리캔버스에 올려 둔 이미지를 쓰고 싶다고 한다.
  "이런 느낌으로"처럼 참고용으로 첨부한 이미지는 등록하지 않는다. 구분 기준은 안내서 `design/user-image`의 "넣을 이미지와 참고 자료"에 있다.
- 요청의 주제 자체가 유명한 밈, 제품, 인물, 로고, 작품, 랜드마크처럼 널리 알려진 실존 대상이다. 예를 들어 밈 소개, 제품 소개, 인물 소개다.
  비슷한 스톡 이미지로는 뜻이 통하지 않는다.
- 요청의 주제가 사용자의 회사, 제품, 팀원처럼 사용자 쪽의 특정 대상인데 그 이미지를 받지 못했다. 웹에서 찾지 않고 사용자에게 이미지를 요청한다.

절차나 구조를 그림으로 그릴지는 템플릿을 고른 뒤 안내서 `design/plan-structure`의 "콘텐츠와 페이지 구성하기"에서 정한다.
템플릿에 그 구조를 표현한 페이지가 있으면 그 페이지를 먼저 쓴다. 사용자가 그려 달라고 했으면 그 페이지가 있어도 그린다.
표 색의 참고 이미지는 등록하지 않고 안내서 `design/plan-data`의 "표 칸 색 지정하기"에 따라 반영할 수 있다.
